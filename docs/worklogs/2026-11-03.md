### (4) 完全削除（`delete_product`）の依存調査と次単位移行に必要な条件（今回は未移行）
1. **Google Drive 画像フォルダ（`AD`列 `drive_folder_url`）**: `ROOT_FOLDER_ID` 配下かつフォルダ名 `=== product_id` を検証の上でゴミ箱へ移動（`setTrashed(true)`）し、後続失敗時は復元する補償処理に依存。Cloud Run 単独では個人マイドライブ権限を持たないため、Drive ゴミ箱移動ブリッジ（または GAS 削除連携）の設計が必要。
2. **仕入書類リンク（Readdy 内蔵 Supabase `document_product_links`）**: 現行 GAS `delete_product` は仕入書類リンクを自動解除しないため、確定リンクが残ったまま商品を削除すると同一仕入明細の再紐付け時に既存リンク競合（`LINE_ALREADY_LINKED_TO_OTHER_PRODUCT`）や `document_lines.match_status` 残存が起きる。移行時は「有効リンク残存時は削除ブロック（先に手動解除）」または「削除前に `documents-relay` でリンク論理削除＋明細/書類ステータス再計算」のいずれかに仕様統一が必要。
3. **独立 Supabase・Google Sheets 子テーブル・再照合**: 独立 Supabase は `ON DELETE CASCADE` で `product_images` / `product_translations` / `pokemon_cards` が連動削除される一方、`product_import_attempts` 等の冪等履歴の扱い（削除後の同一 `import_attempt_id` 再送時の挙動）と、互換ミラー期間中に `reconciler.mjs` が Sheets 残存行から削除済み商品を復活させない同期削除順序の担保が必要。
4. **Square 連携済み商品の削除境界**: `square_item_id` 等を持つアーカイブ商品の削除は Square 在庫0化・決済リンク削除・Catalog Item 削除が先行必須のため、Square 移行完了までは GAS 経路を維持する必要がある。
