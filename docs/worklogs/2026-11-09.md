### (3) 確認・修正 2：200件予約の起動時間と Cloud Scheduler 180秒応答期限の検証・最小対策
- **実測・負荷検証結果（本番200件のAI生成は未実施、読取専用の `get_product_cost` 200件実通信で計測）**:
  - Cloud Scheduler `bis-ec-ai-batch-schedule-dispatch` の `attemptDeadline` は **`180s`**（Cloud Run 側タイムアウトは `300s`）。
  - 本番 `documents-relay`（`action: "get_product_cost"`）に対して読取専用で 200 件の原価照合を実行した実測値：
    1. **コールドスタートを含む初回 200 件（並列度 10）**: 合計 **`55.68秒`**（`55,681ms`、`p50 = 483ms`、`p95 = 13,931ms`、`max = 22,100ms`）。ただし Edge Function コールドスタート時に **200件中3件で一時的な失敗** が発生。
    2. **ウォーム状態の 200 件（並列度 20）**: 合計 **`16.19秒`**（`16,194ms`、`p50 = 269ms`、`p95 = 6,833ms`、`max = 7,577ms`、200/200件成功）。
  - これに Supabase `products` 読取（`< 0.5秒`）・`enqueue_ai_batch_job_atomic` キュー登録（`< 0.5秒`）・非同期ワーカー起動（`0.25秒`）を加えても、200件予約1本の起動時間は **約17秒（ウォーム時）〜約57秒（コールド時）** であり、180秒の応答期限に十分収まることを確認。
- **適用した3つの最小対策（`aiDraftService.mjs` / `aiBatchService.mjs`、Cloud Run `bis-ec-products-api-00018-rvv` 配信済み）**:
  1. **原価取得の単発タイムアウト（15秒）＋一時エラー時の自動リトライ（最大3回、バックオフ `250ms`/`500ms`）**:
     - コールドスタート時の一時的な HTTP `408`/`429`/`5xx` や通信タイムアウトで200件予約全体が `dispatch_retry` に倒れないよう、`fetchProductCostFromDocumentsRelay` 内で最大3回まで自動再試行（3回すべて失敗した場合は従来どおり Fail-Closed で `PRODUCT_COST_FETCH_FAILED` とし、原価なしでの生成は行わない）。
  2. **20件以上のバッチでの先行1件ウォームアップ**:
     - `resolveConfirmedProductCostsForBatch` で `productIds.length >= 20` の場合、最初の1件で `documents-relay` を先行ウォームアップしてから残り199件を並列度 `12`（`COST_LOOKUP_CONCURRENCY = 12`）で取得し、コールドスタート時のスパイクを抑止。
  3. **ディスパッチの1件ずつ取得（`p_limit: 1`）と時間予算（`DISPATCH_TIME_BUDGET_MS = 90_000` = 90秒）**:
     - 同一時刻に複数の200件予約が重なった場合でも 180秒期限を超過しないよう、`dispatchDueAiBatchSchedules` は1ループにつき1予約ずつ claim し、経過時間が 90秒に達した時点で残りの予約を次分（1分後）の Cloud Scheduler 起動へ安全に持ち越す。
